# Хранилище броней — SQLite

_Реализация отложена: первый срез проекта — статичный лендинг без серверной логики. Решение вступает в силу, когда появится бронирование._

Брони должны переживать перезапуск процесса, а «проверка конфликта при бронировании» обязана быть честной, а не имитацией. Храним брони в SQLite через `better-sqlite3`, за интерфейсом-репозиторием.

> Уточнено (карта решений, тикет «Правило занятости и пересечения»): занятость считается по пересечению интервалов `[start, start+duration)` между разными типами; уникальный индекс по точному началу этого не покрывает, поэтому запрет второй записи делается транзакционной проверкой в приложении, а не индексом.

## Considered Options

- **In-memory** — проще всего, но данные теряются при рестарте и гонку нужно защищать руками.
- **JSON-файл** — переживает рестарт, но атомарность и конкурентный доступ решаются вручную.
- **Postgres** — лишний операционный и CI-сервис для учебного односервисного проекта.
